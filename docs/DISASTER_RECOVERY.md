# תוכנית התאוששות מאסון – מערכת עלמא

## מה מגובה ואיפה
| מה | תדירות | איפה | כמה זמן נשמר |
|---|---|---|---|
| גיבוי מלא (מסד נתונים + כל הקבצים המוצפנים) | פעם ביום (אחרי 02:00) | שרת + גוגל דרייב | שרת: 7 ימים + 4 ראשונים. דרייב: 14 ימים + 8 ראשונים + 6 חודשים |
| דלתא (רק שורות/קבצים שהשתנו) | כל 10 דקות | שרת + גוגל דרייב | 3 ימים |

כל הקבצים מוצפנים (AES-256-GCM) במפתח `private/app.key`. **בלי המפתח אי אפשר לפתוח אף גיבוי**, והוא לא נמצא בגיבוי.
מקסימום אובדן נתונים (RPO): כ-10 דקות. זמן שחזור צפוי (RTO): כשעה כולל התקנה מחדש.

## מה חייב להיות מחוץ לשרת (לפני שקורה אסון!)
1. **ערכת שחזור**: דף "גיבויים" ← "הורדת ערכת שחזור". מכילה את `app.key` ואת `config.php`. שמרו אצלכם + שלחו לעצמכם במייל. הורידו מחדש אחרי כל שינוי בהגדרות.
2. הגישה לתיקיית הדרייב (החשבון שבו הוגדרו הגיבויים).
3. גישה למאגר הקוד ב-GitHub (`almadevteam-ops`).

## תרחיש א: מחיקה/טעות בנתונים (השרת תקין)
שחזור לנקודת זמן **לבסיס נתונים נפרד** והשוואה, בלי לגעת במערכת החיה:
1. ב-cPanel צרו בסיס נתונים חדש ריק ומשתמש עם הרשאות עליו (למשל `almascho_restore`).
2. במסוף (Terminal) או Cron חד-פעמי:
   ```
   php private/cron/restore.php chain --src=private/backups --db=almascho_restore --db-user=USER --db-pass=PASS \
       --storage=/home/USER/restore_storage --to="2026-11-11 14:30"
   ```
   בלי `--to` משחזרים את הנקודה האחרונה. הפקודה לוקחת את הגיבוי המלא האחרון לפני הזמן שביקשתם, ומחילה עליו את כל הדלתאות עד אותה דקה.
3. מוצאים ב-phpMyAdmin את השורות החסרות בבסיס הנתונים המשוחזר ומעתיקים אותן, או מחליפים את המערכת החיה (תרחיש ב).

## תרחיש ב: אובדן מלא של השרת/החשבון
1. פותחים חשבון אחסון חדש (או מנקים את הקיים), PHP 8.3 + MySQL, ויוצרים בסיס נתונים ריק + משתמש.
2. מעלים את הקוד: cPanel ← Git Version Control ← Clone של המאגר, ואז Deploy HEAD Commit.
3. משחזרים מהערכה (מהמייל / מהשמירה שלכם): `private/app.key` ו-`private/config.php` (מעדכנים בו את פרטי בסיס הנתונים החדש אם השתנו). **קודם המפתח, לפני כל דבר אחר.**
4. מורידים מהדרייב לתיקיה אחת (למשל `private/backups`) את **הגיבוי המלא האחרון + כל הדלתאות שאחריו**. אפשר להוריד הכול מהתיקיה.
5. בודקים את הרצף: `php private/cron/restore.php list --src=private/backups` (מציג את הרצף ואזהרה אם חסרה חוליה).
6. משחזרים: 
   ```
   php private/cron/restore.php chain --src=private/backups --db=DBNAME --db-user=USER --db-pass=PASS \
       --storage=/home/USER/private/storage --yes-live
   ```
   (`--yes-live` נדרש כשזה בסיס הנתונים שהוגדר ב-config; `--wipe` אם הוא לא ריק.)
7. מריצים את הדף "עדכון מסד נתונים" אם יש מיגרציות חדשות מהגיבוי.
8. מגדירים מחדש את ה-cron כל 10 דקות (דף "גיבויים" מציג את השורה המדויקת).

### רשימת בדיקה אחרי שחזור
- [ ] התחברות עם משתמש מנהל מצליחה (כולל אימות דו-שלבי).
- [ ] פתיחת כרטיס תלמידה עם מסמכים מצורפים (הקובץ נפתח – מוכיח שהמפתח נכון).
- [ ] מספר התלמידות והתשלומים תואם למה שציפיתם.
- [ ] דף "בדיקת מערכת" ירוק; "יומן גיבויים" מראה גיבוי מלא חדש תוך שעה.
- [ ] הגדרת הדרייב עדיין עובדת ("בדיקת חיבור" בדף גיבויים).
- [ ] הרצה ידנית של "גיבוי מלא עכשיו" מצליחה.

## תרגיל שחזור (מומלץ אחת לרבעון)
שחזרו את הנקודה האחרונה לבסיס נתונים נפרד (תרחיש א, בלי `--to`), ובדקו את רשימת הבדיקה מול הנתונים החיים. הבדיקה האוטומטית השבועית ("בדיקת תקינות" ביומן הגיבויים) מוודאת שהקובץ נפתח ושהעותק בדרייב זהה בגודלו, אך רק שחזור אמיתי מוכיח שהכול עובד.

## הערות
- אם רצף הדלתאות שבור (קובץ חסר), הכלי משחזר עד החוליה השבורה ומדווח אזהרה (קוד יציאה 3).
- אם המסד נפל ולא ניתן לשמור יומן, הרישום נשמר בקובץ `private/backups/log-fallback.jsonl`.
- אם ה-cron עצמו נעצר לא יישלח מייל; דף "יומן גיבויים" מציג התרעה אדומה כשעברו יותר מ-25 דקות.
